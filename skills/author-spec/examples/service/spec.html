01Objective and scope

Retrying a job-submission request must not create a second job for the same tenant and request key.

Scope
IncludedExcluded
Tenant-scoped idempotency for authenticated POST /jobs; conflict detection; replay of the committed response.New queue services, job execution changes, automatic key expiration, and cross-tenant deduplication.

02Behavior and external contract

Submission protocol
ConditionResultDurable effect
Valid new key and valid request201 with the job response.One job and one replay record, committed together.
Same tenant, key, and exact request bytesReplay the original status, content type, and response body.No second job.
Same tenant and key; different request bytes409; no job details from other tenants.No additional job.
Missing key or key outside 1–128 printable ASCII characters400.No writes.
Database unavailable or commit outcome uncertain503; retry with the same key.A later replay resolves a previously committed request.
POST /jobs
Idempotency-Key: client-generated-key
Content-Type: application/json

{"type":"report","period":"2026-10"}

Request equivalence is byte-for-byte equality of the validated JSON request body, represented by SHA-256. Semantically equivalent JSON with different bytes is a conflict. Authentication and existing payload validation still run before submission.

04Acceptance criteria

Observable requirements and proposed verification
IDRequirementRepresentative verification
AC-001One valid new request creates one job and returns its committed response.Handler/service integration case and row-count assertions.
AC-002Sequential and concurrent equal requests produce one job and the same response.Concurrent requests against real PostgreSQL, with separate connections.
AC-003Different payload bytes for the same tenant/key return 409 without another job.Payload mismatch and concurrency cases.
AC-004The same key in different tenants is independent; unauthorized requests cannot observe replay records.Two authenticated tenants and a rejected caller.
AC-005Invalid input and rolled-back transactions leave no partial job/replay pair.Validation cases and transactional failure injection.
AC-006A retry after response loss or service restart replays the durable response.Discard the first HTTP response, restart the service, then retry the same request.
